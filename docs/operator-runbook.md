# Operator runbook

One page for whoever installs, supports, or releases the Flisk CLI. Details live in the linked pages.

## Install and support matrix

| Host | `flisk up` | Other commands |
| --- | --- | --- |
| macOS | supported | supported |
| Linux | supported | supported |
| WSL2 Ubuntu | supported (see [wsl2.md](wsl2.md)) | supported |
| Native Windows | not supported; refuses with "Native Windows is inspect-only" | inspect-only |

`flisk up` needs Docker and Tilt on the host. Run `flisk doctor` to check them.

## Generated files and drift

For a file-by-file guide to service outputs, see [Generated service files](generated-files.md).

`flisk up` checks generated service files (under `.autogenerated/`) against their snapshot before Tilt starts. Editing `service.json` and running `flisk up` is the normal loop and is not drift: `flisk up` regenerates the outputs.

- If a generated service file was edited by hand, `flisk up` exits 2 and lists it. Restore the saved content or move the intended change into `service.json`; the CLI also suggests `flisk config regenerate`, which rewrites project files rather than the service output itself.
- `flisk config verify` runs a wider check: it compares generated project files, validates discovered service manifests, and checks generated service snapshots. It prints diffs for project files and names service errors.
- `flisk up --dry-run` runs the same check and exits 2 on drift, so you can see it without starting anything.
- `flisk up --ignore-drift` skips the check and always prints a warning, whether or not anything drifted, because the check did not run.
- A missing `.tdk-contract` snapshot is reported by `flisk config verify` as an error, but it does not block `flisk up`: only files that differ from an existing snapshot count as hand edits. A project with no `.tdk/project.json` is not checked.

## Importing an existing repo

`flisk import` runs the published importer, [`flisk-import`](https://www.npmjs.com/package/flisk-import), at the exact version pinned in `cli/src/commands/import.ts` (`IMPORT_PACKAGE`). `TDK_IMPORT_PACKAGE` overrides it. When a new importer is published, move the pin in a CLI release.

It reads one file, the root `docker-compose.yml`, and writes one bring-your-own `service.json` per Compose service, plus `.tdk/project.json` if the directory is not a Flisk project. It does not read other Compose file names, override files, Dockerfiles, `package.json` or Procfiles, and it names what it did not translate. See the importer's [import.md](https://github.com/flisk-sh/flisk-import/blob/main/docs/import.md) for the mapping.

```bash
flisk import <dir> --dry-run
flisk import <dir> --yes
```

Start the imported stack with Flisk core **1.3.145 or later**. 1.3.104 added `buildContext` ([flisk#525](https://github.com/flisk-sh/flisk/pull/525)); 1.3.145 generates the Tiltfile for a project that has `.tdk/project.json` but none yet ([flisk#1018](https://github.com/flisk-sh/flisk/pull/1018)). `flisk import` enforces that the installed core is at least 1.3.104 before writing; if an older core is encountered, it exits before writing and prints the upgrade command (`flisk upgrade`).

Put the environment values the services need in the project `.env`; values in the Compose file are never copied. Evidence of the importer running through a real `flisk up`: [#1007](https://github.com/flisk-sh/flisk/issues/1007).

## Cutting a release

> The current ops checklist — pipeline order, candidate and dispatch commands, repair recipes, the unscoped npm package, and troubleshooting — is [Release operations](releasing.md). This section keeps the background: npm authentication, what past releases taught us, and the publish gate.

> [!WARNING]
> The automatic version bump does not work as expected yet. After the 1.3.185 release, the git tag `v1.3.185` pointed at a commit whose `package.json` still said `1.3.184`, and `bun.lock` was never bumped. npm and the GitHub release had the right version. Check the tag, `package.json`, `cli/package.json` and `bun.lock` after every release until these are fixed: [#1657](https://github.com/flisk-sh/flisk/issues/1657), [#1658](https://github.com/flisk-sh/flisk/issues/1658), [#1659](https://github.com/flisk-sh/flisk/issues/1659).

### How the npm publish authenticates

The release workflow publishes with **npm trusted publishing (OIDC)**, so there is no long-lived npm token in the repository and no browser approval per release. The publish job already holds `id-token: write`, and it installs npm 12.2.0 because trusted publishing needs npm ≥ 11.5.1.

The trusted publisher is configured once, on npm:

```bash
npm trust github @flisk-sh/flisk \
  --file release-binaries.yml \
  --repo flisk-sh/flisk \
  --allow-publish
```

`npm trust list @flisk-sh/flisk` shows it, and `npm trust revoke @flisk-sh/flisk --id <id>` removes it. The same thing can be done in the npm UI: open the package, **Settings → Trusted Publisher → GitHub Actions**, then fill in organization `flisk-sh`, repository `flisk`, workflow filename `release-binaries.yml`, and allow `npm publish`.

If the repository also has an `NPM_TOKEN` secret, the workflow uses it and skips OIDC; that is the fallback for forks that have no trusted publisher configured. `NODE_AUTH_TOKEN` is only exported when the secret exists, because an empty one makes npm attempt token auth and fail with `EOTP` instead of falling back to OIDC.

### Lessons from release 1.3.187 (2026-10-20)

- The first release-candidate run passed 28 component jobs but failed two frontend jobs because Docker Compose did not respond within the suite's 10-second readiness check. A retry on the same commit passed all 31 jobs. When multiple independent runners fail at the same infrastructure readiness check, inspect their uploaded diagnostics and retry the candidate once; do not bypass the candidate gate.
- A candidate on a release branch is stable while `main` advances. The first publish attempt was dispatched on `main` and correctly stopped because the candidate did not cover the current release inputs. Run both the candidate and release workflows on the same `release/rc-*` ref.
- Publication can succeed before the workflow finishes. Version 1.3.187 reached npm and the `flisk-sh/releases` repository, but the workflow later failed when branch protection rejected its direct push of `release/bump-1.3.187`. The signing and provenance steps were consequently skipped. Confirm npm availability after its processing delay, then check the release assets and workflow steps separately; a failed workflow does not necessarily mean nothing was published.
- The automatic version-bump step must create a branch through an allowed PR workflow, not rely on a direct branch push that violates repository rules. After publication, verify `package.json`, `cli/package.json`, the changelog, and lockfile state on `main`, and ensure the version bump PR exists and is tracked.

### Suggested release workflow improvements

1. Make the version-bump step create a PR using an approved GitHub App or other credential allowed by branch rules, and treat PR creation as a distinct post-publication task. Add a workflow test or dry-run check that detects a branch-rule rejection before shipping.
2. Separate publication success from post-release bookkeeping in workflow status. A failure to open the version-bump PR or attach provenance should be surfaced as an incomplete follow-up without obscuring that npm and binary publication succeeded; report the exact published destinations and remaining steps in the summary.
3. Give the Docker Compose readiness check a bounded retry/backoff and preserve the existing failure diagnostics. Keep candidate checks blocking: retry transient runner startup failures, but never mark a candidate successful by skipping the suite.
4. Add a post-publish verification step that retries npm metadata lookup during the registry processing window and verifies the npm version and tarball, release tag/assets, checksum signature, and provenance independently.

The normal release is the workflow, from a release branch (see the publish gate in [#1631](https://github.com/flisk-sh/flisk/pull/1631)):

1. Cut `release/rc-<timestamp>` at the commit to ship, and run the Release candidate workflow on it. Wait for it to pass.
2. Run `gh workflow run release-binaries.yml --ref release/rc-<timestamp>`. The workflow picks the next unpublished version, builds and checks the binaries, publishes the npm package and the release in `flisk-sh/releases`, and credits fixed issues.
3. The workflow signs the checksums, then opens a `Release <version> (automatic version bump)` PR so `main` matches npm; merging it tags `v<version>` and publishes the checksums release. If a step fails after publication, follow [Repair a half-finished release](releasing.md#repair-a-half-finished-release) instead of re-dispatching.
4. The installer verifies each binary against `checksums.txt`.

To build a binary by hand, without publishing, run `scripts/release-binaries.sh`. It writes `tdk-linux-{amd64,arm64}`, `tdk-darwin-{amd64,arm64}`, `tdk-windows-amd64.exe`, `tdk-cli-engine.tar.gz`, and `checksums.txt` (SHA-256) into `release-dist-<version>/`. `scripts/release-binaries.sh --publish` creates a draft release, downloads every asset, compares bytes with the local build, and only then publishes it as latest. `--publish-only` reuses an existing `release-dist-<version>/`.

### Publish gate

`release-binaries.yml` publishes to npm only when a passing **Release candidate** run (`release-candidate.yml`) covers the commit being released. Dispatch the release on `main`, and the `publish` job checks this first with `scripts/check-release-candidate.mjs`:

- **Exact commit:** a passing candidate ran on the same commit. This is the normal case.
- **Ancestor commit:** a passing candidate ran on an earlier commit, and no commit since changed a release input. The release inputs are the paths the `changes` job filters on (`cli/**`, `engine/**`, `package.json`, `bun.lock`, `Tiltfile`, `discovery/**`, `specs/**`, `ext/**`, `scripts/release-binaries.sh`, `shared-platform-engineering/docker-templates/**`, and `release-binaries.yml` itself). CI-only and docs-only commits do not invalidate a candidate.
- **Otherwise** the gate fails and lists, for each candidate, why it does not cover the commit (for example `release inputs changed since (cli/**)`). Run a new candidate on the commit, then re-run publish.

**Release from a `release/*` branch.** `main` moves every few minutes, so a candidate on `main` is stale before it finishes. Release from a branch instead:

1. Cut `release/rc-<timestamp>` at the commit to ship: `git push origin <commit>:refs/heads/release/rc-<timestamp>`.
2. Run the Release candidate workflow on that branch: `gh workflow run release-candidate.yml --ref release/rc-<timestamp>`.
3. When it passes, run the release on the same branch: `gh workflow run release-binaries.yml --ref release/rc-<timestamp>`. The gate then matches the exact commit, and `main` can keep moving.
4. Bring the version bump back to `main` through a normal PR. Do not force-push `main` or the release branch.

Candidates are not run on every push, so a dispatch on `main` fails until a candidate covers its commit. Check any commit with the gate before you dispatch:

```bash
GH_TOKEN="$(gh auth token)" node scripts/check-release-candidate.mjs --sha <commit> --repo flisk-sh/flisk
```

Tracked in [#1627](https://github.com/flisk-sh/flisk/issues/1627).

## License key

`TDK_LICENSE_KEY` is optional. `flisk up` still runs the free stack when the key is unset, invalid, or expired. The cases differ in what `flisk up` does:

| Key state | Premium-bundle request | Premium overlay |
| --- | --- | --- |
| Unset | none | none; Verdaccio and Sablier fall back to disabled public stubs and print a message that they need a license |
| Invalid or expired | made, unless a cached result is still fresh | none for a rejected key; an overlay already in `.tdk/.tdk-out/tdk-cli-ext` stays in use |

- Bundle downloads and entitlement checks (grant or denial) are cached per key under `~/.tdk/cache` and reused for up to 12 hours. For that window a key that was just revoked or has just expired can still be treated as entitled, and a key that was denied is not re-checked until the cache expires. Operators will hit this most often.
- `flisk up` does not revalidate the key or re-vendor `.tdk/.tdk-out/tdk-cli-ext`. A premium overlay created while the key was valid can stay in use after the key expires.
- DDD is public code gated separately by `flisk resource --ddd`; it is not a stub.
